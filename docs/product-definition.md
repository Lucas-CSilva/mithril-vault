## Part 1: Foundational Technical Decisions

These decisions are finalized and must be respected uniformly across the entire stack. They are not open for revision without updating this document and all affected specs.

### Money Representation — Minor Units (Centavos)

All monetary values are stored and transmitted as `Long` integers representing **centavos** (1 real = 100 centavos). This eliminates floating-point rounding errors entirely.

| Layer | Type | Notes |
|---|---|---|
| Java domain/DTOs | `Long` | All monetary fields |
| MongoDB (BSON) | `Int64` | Never `Double` |
| JSON API | `number` (integer) | e.g., `150090` = R$ 1.500,90 |
| Frontend display | `number` formatted via `toLocaleString` | Format only at render time |

**Overflow safety**: `Long.MAX_VALUE` in centavos ≈ R$ 92 trilhões — safe for personal finance.

**Percentage arithmetic rule — always multiply before dividing:**

```java
// ✓ Correct — multiply first, then divide
long ir = (grossYield * 225) / 1000;  // 22.5% = 225/1000

// ✗ Wrong — integer division truncates precision
long ir = grossYield / 1000 * 225;
```

**Frontend formatting:**

```typescript
const formatBRL = (centavos: number): string =>
  (centavos / 100).toLocaleString('pt-BR', { style: 'currency', currency: 'BRL' });
// 150090 → "R$ 1.500,90"
```

**API contract rule**: Every endpoint spec must document monetary fields as integers representing centavos. Example: `"amount": 150090` means R$ 1.500,90. Decimal values are never sent over the wire.

## Part 2: Core Data Model

### Entities and Relationships

```
User
 ├── has many Accounts
 ├── has many CreditCards
 │    └── each CreditCard has many Invoices (Faturas)
 │         └── each Invoice has many Transactions
 ├── has many Transactions (linked to Account)
 ├── has many Categories (user-defined only; system categories are global)
 ├── has many Budgets (monthly, per category)
 ├── has many Goals (Cofres)
 ├── has many Investments
 └── has many Subscriptions
```

### Entity Definitions

#### Account (Conta)

Represents any source of liquid funds the user controls directly.

| Field | Type | Notes |
|---|---|---|
| id | UUID | |
| name | String | e.g., "Nubank", "Bradesco Corrente" |
| type | Enum | CHECKING, SAVINGS, CASH, DIGITAL |
| institution | String | Bank name, optional |
| initialBalance | Long | Balance in centavos at the moment the account was added |
| color | String | Hex, for UI identification |
| isActive | Boolean | Soft-delete — never hard-delete accounts |
| createdAt | Instant | |

**Balance rule**: `currentBalance` is always **derived** — never stored. Computed as:

```
currentBalance = initialBalance + sum(CREDIT transactions) - sum(DEBIT transactions)
```

`initialBalance` anchors the calculation to the real-world balance on the day the account was added to the app. Manual reconciliation (see Module 2) adjusts `initialBalance` when drift is detected.

#### Invoice (Fatura)

One billing cycle of a credit card. Auto-generated by the system each month.

| Field | Type | Notes |
|---|---|---|
| id | UUID | |
| creditCardId | UUID | FK to CreditCard |
| referenceMonth | YearMonth | e.g., 2025-01 |
| closingDate | LocalDate | Computed from card's closingDay |
| dueDate | LocalDate | Computed from card's dueDay |
| status | Enum | OPEN, CLOSED, PAID |
| paidAt | Instant | Nullable |
| paidFromAccountId | UUID | Nullable — account used to pay |

**totalAmount** is always derived: sum of all transactions in this invoice. Never stored.

**Status transitions**:
- `OPEN → CLOSED`: automatically on closingDate, or manually triggered by user
- `CLOSED → PAID`: manually when user registers payment

**Payment effect**: marking an invoice PAID automatically creates a DEBIT transaction on the `associatedAccount` for the invoice total. The user may adjust the amount if they paid less than the full total (minimum payment scenario). The invoice is marked PAID regardless — partial payment tracking is handled by the user's notes, not a separate system state.

#### Transaction (Transação)

Every money movement in the system. The single source of truth for all balances.

| Field | Type | Notes |
|---|---|---|
| id | UUID | |
| type | Enum | DEBIT (saída), CREDIT (entrada) |
| amount | Long | Centavos, always positive |
| date | LocalDate | When it occurred, not when it was entered |
| description | String | From bank statement or user-entered |
| categoryId | UUID | FK to Category |
| paymentMethod | Enum | PIX, TED, DOC, DEBIT_CARD, CREDIT_CARD, BOLETO, CASH, TRANSFER |
| accountId | UUID | Nullable |
| invoiceId | UUID | Nullable |
| tags | List\<String\> | User-defined labels |
| notes | String | Free text |
| isRecurring | Boolean | |
| recurringSeriesId | UUID | Groups recurring instances |
| installmentSeriesId | UUID | Groups parcelamento installments |
| installmentNumber | Int | e.g., 2 |
| totalInstallments | Int | e.g., 6 |
| transferPairId | UUID | Links the two legs of a transfer |
| importHash | String | SHA-256(date + normalizedDescription + amount) |
| importSource | Enum | Nullable: MANUAL, CSV, OFX |
| createdAt | Instant | |

**Constraint**: exactly one of `accountId` or `invoiceId` must be non-null. A transaction lives in an account or in a credit card invoice — never both, never neither.

**Transfer rule**: A transfer between two accounts creates exactly two transactions — one DEBIT from the source and one CREDIT to the destination — linked via `transferPairId`. Transfers are excluded from income/expense totals on the dashboard.

**Recurring series edit rule**: when a user edits a recurring transaction, all instances from the edited occurrence forward are updated. Past instances are immutable. Implementation: delete and regenerate all future instances from `editedFromDate`, using the updated series parameters.

**Split transactions**: not supported. One transaction maps to exactly one category.

#### Category (Categoria)

Hierarchical, two levels deep: top-level → subcategory.

| Field | Type | Notes |
|---|---|---|
| id | UUID | |
| name | String | |
| parentId | UUID | Null = top-level category |
| icon | String | |
| color | String | Hex |
| isSystem | Boolean | System categories cannot be edited or deleted |
| userId | UUID | Null for system categories |

**System categories** (global, indestructible):
Alimentação, Moradia, Transporte, Saúde, Educação, Lazer, Vestuário, Serviços & Assinaturas, Investimentos, Transferências, Renda, **Outros**

**User category deletion rule**: when a user-defined category is deleted, all its transactions are reassigned to the system "Outros" category via a bulk update before deletion. Deletion is never blocked. System categories cannot be deleted under any circumstance.

**Budget aggregation rule**: a budget on a parent category counts transactions from all its subcategories. Queries filter by `categoryId IN (parentId, child1Id, child2Id, ...)`. Since the hierarchy is only two levels deep, descendant resolution is always a single query with no recursion needed.

| month | YearMonth | |
| limitAmount | Long | Centavos |
| isRecurring | Boolean | If true, auto-creates for future months |

**spentAmount** is always derived: sum of DEBIT transactions matching the category (and all descendants) in the budget's month. Never stored.

#### Goal (Meta / Cofre)

A savings objective.

| Field | Type | Notes |
|---|---|---|
| id | UUID | |
| name | String | |
| targetAmount | Long | Centavos |
| currentAmount | Long | Manually updated by user |
| deadline | LocalDate | Nullable |
| linkedAccountId | UUID | Nullable |
| icon | String | |
| color | String | |
| status | Enum | IN_PROGRESS, COMPLETED, ABANDONED |

**Projection rule**:
- With deadline: `requiredMonthly = (targetAmount - currentAmount) / monthsUntilDeadline`
- Without deadline: `projectedMonths = (targetAmount - currentAmount) / avgMonthlyContribution` (average of last 3 months of manual updates)

Goals are a **tracking layer** — they do not move money between accounts. Users update `currentAmount` manually when they set aside funds.

#### Investment (Investimento — Renda Fixa)

Fixed-income investments held outside of liquid accounts.

| Field | Type | Notes |
|---|---|---|
| id | UUID | |
| name | String | e.g., "CDB Nubank 110% CDI" |
| type | Enum | CDB, TESOURO_SELIC, TESOURO_IPCA, TESOURO_PREFIXADO, LCI, LCA, CRI, CRA, DEBENTURE |
| institution | String | |
| investedAmount | Long | Original principal, centavos |
| currentGrossValue | Long | User-updated; defaults to investedAmount on creation |
| rateType | Enum | CDI_PERCENTAGE, IPCA_PLUS, PREFIXADO, SELIC_PERCENTAGE |
| rateValue | Long | Rate × 100 to avoid decimals — e.g., 11000 = 110,00% CDI; 650 = 6,50% |
| startDate | LocalDate | |
| maturityDate | LocalDate | Nullable |
| liquidityType | Enum | DAILY, AT_MATURITY, SPECIFIC_DATE |
| liquidityDate | LocalDate | Only when SPECIFIC_DATE |
| isIRExempt | Boolean | True for LCI, LCA |
| status | Enum | ACTIVE, MATURED, REDEEMED |
| redeemedAt | LocalDate | Nullable |
| redeemedAmount | Long | Nullable — actual net amount received |
| createdAt | Instant | |

**IR table (non-exempt investments — CDB, Tesouro)**:

| Days held | IR rate |
|---|---|
| Up to 180 | 22,5% |
| 181 – 360 | 20,0% |
| 361 – 720 | 17,5% |
| Over 720 | 15,0% |

**Net value estimate**:
```
grossYield    = currentGrossValue - investedAmount
irRate        = irRateFromTable(daysSinceStart)   // 0 if isIRExempt
estimatedIR   = (grossYield × irRate) / 10000     // irRate stored as integer × 100
netValue      = currentGrossValue - estimatedIR
```

Displayed as an **estimate**. Actual tax depends on the broker's calculation and exact daily rates.

**Account integration (optional)**: when creating an investment, a checkbox "Registrar débito na conta" lets the user create a corresponding DEBIT transaction on a source account. On redemption, a checkbox "Registrar crédito na conta" creates a CREDIT transaction on a destination account. This keeps liquid balances accurate for users who want full double-entry tracking.

**Rate storage**: `rateValue` is stored as an integer × 100 to avoid decimals. 110% CDI = `11000`. IPCA+6,50% = `650`. Display divides by 100.

#### Subscription (Assinatura)

A recurring charge on a known schedule.

| Field | Type | Notes |
|---|---|---|
| id | UUID | |
| name | String | |
| billingCycle | Enum | MONTHLY, BIMONTHLY, QUARTERLY, SEMIANNUAL, ANNUAL |
| nextChargeDate | LocalDate | |
| categoryId | UUID | |
| paymentMethod | Enum | |
| creditCardId | UUID | Nullable |
| status | Enum | ACTIVE, PAUSED, CANCELLED |
| cancelledAt | LocalDate | Nullable |
| notes | String | |
| linkedTransactionPattern | String | Keyword for auto-matching imports |
| priceHistory | List\<PriceEntry\> | See below |

**Price history**: `amount` is never stored directly on Subscription. It is the `amount` of the latest entry in `priceHistory`. When the user updates the price, a new entry is appended — existing entries are never modified.

```
PriceEntry {
  amount:    Long        // centavos
  validFrom: LocalDate   // first day this price was in effect
}
```

This makes the full price change timeline available for annual cost analysis, even across years.

**Monthly equivalent cost** (for summary totals):

| Cycle | Multiplier |
|---|---|
| MONTHLY | × 1 |
| BIMONTHLY | × 0.5 |
| QUARTERLY | × 0.333 |
| SEMIANNUAL | × 0.1667 |
| ANNUAL | × 0.0833 |

## Part 3: Module Specifications

### Module 1: Dashboard & Overview

**Purpose**: Instant, complete picture of financial health. Every number must be accurate and current.

#### Saldo Líquido Disponível (Hero)

The most prominent number on the screen.

```
Saldo Líquido = sum(all active account balances) - sum(all OPEN invoice totals)
```

Subtracting open invoices is what makes this number honest — it reflects money that is actually available, not money that is nominally in the bank but already committed to a fatura.

#### KPI Cards (current calendar month)

- **Receitas**: sum of all CREDIT transactions (excluding transfer credits)
- **Despesas**: sum of all DEBIT transactions (excluding invoice payments and transfer debits)
- **Investido no mês**: sum of investment-linked debits this month
- **Saldo do mês**: Receitas − Despesas

#### Gráfico de Fluxo de Caixa

Spline line chart of total liquid balance over time. Toggles: 7 days / 30 days / 3 months / 12 months. Y-axis = total liquid balance at end of each day.

#### Distribuição de Gastos

Donut chart of current month expenses by top-level category. Clicking a slice expands to subcategory breakdown. Shows both absolute value and percentage per slice.

#### Radar de Obrigações (next 7 days)

Sorted by due date ascending:
- Credit card faturas due within 7 days
- Active subscriptions with `nextChargeDate` within 7 days

Each item shows: name, amount, days until due.
Urgency colors: green (> 5 days), yellow (3–5 days), red (≤ 2 days).

#### Orçamentos do mês

Progress bars for all active budgets in the current month. Green below 80%, yellow 80–99%, red ≥ 100%.

### Module 2: Accounts & Transactions

**Purpose**: Every money movement is created and managed here.

#### Account Management

- Account list: name, type, institution, current balance (derived), color
- Create account: name, type, institution (optional), initial balance (real current balance on the day of creation), color
- Account detail: balance history chart + filtered transaction feed for that account
- Soft-delete only — deactivating an account hides it from the UI but preserves all transactions and historical balance data

**Reconciliation**: The user enters the actual balance from their bank statement. The system shows the discrepancy. The user chooses to create an adjusting transaction ("Reconciliação" label, CREDIT or DEBIT) or update `initialBalance` directly. Adjusting transactions are flagged visually in the feed so they are clearly not real bank movements.

#### Transaction Feed

Global (all accounts merged) or per-account view. Sorted by date descending.

**Row shows**: date, description, category icon + name, amount (red = debit, green = credit), payment method tag, source account/card name.

**Filters**: date range, account, category, payment method, type, text search on description.

#### Adding a Transaction (Manual)

Required: type, amount, date, description, destination (account or credit card).
Optional: category (auto-suggested by keyword), payment method, tags, notes, recurring.

**Credit card transactions**: user picks the card; the system assigns to the correct open invoice based on whether the transaction date is before or after `closingDay`.

**Parcelamento**: enabled on credit card transactions only. User enters total number of installments. System creates N transactions of `amount ÷ N` (centavos — integer division, with any remainder centavo added to the first installment) across N consecutive invoices. Each transaction shows "2/6 parcelas".

**Recurring transactions**: user sets frequency (weekly, monthly, etc.) and optional end date. System generates instances up to 12 months ahead. Edit behavior: editing any instance updates all future instances from that point forward (past instances are immutable).

#### Import Flow (CSV + OFX)

1. User uploads file
2. System detects format (OFX is auto-parsed; CSV requires column mapping)
3. **CSV column mapping**: on first import from a new source, user maps date/description/amount columns. Mapping is saved per source name (user-given label) and reused on subsequent imports
4. System shows preview table of all parsed transactions
5. Rows matching an existing `importHash` (or OFX `FITID`) are flagged as probable duplicates and pre-unchecked — user can manually re-check them to force import
6. System auto-suggests categories via keyword matching on description
7. User reviews, adjusts categories, and confirms
8. Transactions are created; account balance updates immediately

**Deduplication keys**:
- OFX: `FITID` field (provided by the bank — unique per transaction)
- CSV: `SHA-256(date + normalizedDescription + amount)` where normalization is uppercase + collapse whitespace

**Category auto-suggestion keywords** (initial set, expandable):

| Description contains | Suggested category |
|---|---|
| SUPERMERCADO, MERCADO, CARREFOUR, EXTRA, ATACADÃO | Alimentação > Supermercado |
| IFOOD, RAPPI, UBER EATS, DELIVERY | Alimentação > Delivery |
| RESTAURANTE, LANCHONETE, PADARIA | Alimentação > Restaurante |
| POSTO, SHELL, PETROBRAS, COMBUSTIVEL | Transporte > Combustível |
| UBER, 99, CABIFY, LYFT | Transporte > Aplicativo |
| FARMACIA, DROGARIA, DROGA RAIA, ULTRAFARMA | Saúde > Farmácia |
| NETFLIX, SPOTIFY, AMAZON PRIME, DISNEY, HBO | Serviços > Streaming |
| SALARIO, PAGAMENTO SALARIO, FOLHA | Renda > Salário |
| PIX RECEBIDO | Renda > Transferência recebida |
| ALUGUEL | Moradia > Aluguel |
| ENERGIA, LIGHT, ENEL, CEMIG | Moradia > Energia |
| AGUA, SABESP, COPASA | Moradia > Água |

### Module 3: Card Management

**Purpose**: Manage credit card limits, fatura lifecycle, and billing cycle intelligence.

#### Card Wallet

CSS-rendered card mockup (no real card images). Each card shows: last 4 digits, institution, credit limit, utilized amount, available limit, progress bar (green → yellow → red as utilization rises), closing date, due date.

Available limit = `creditLimit - currentOpenInvoiceTotal`.

#### Invoice Cycle Monitor

Per-card view with a tab strip for: past 3 months + current month + next month.

Each fatura tab shows:
- Status badge (OPEN / CLOSED / PAID)
- Closing date and due date
- Total amount (derived)
- Transaction list for that invoice

**Melhor dia de compra**: `closingDay + 1`. Prominently displayed. A purchase on this day goes into the next fatura, maximizing the interest-free period. Example: closing day = 3rd → best purchase day = 4th.

**Paying a fatura**:

1. User clicks "Registrar Pagamento" on a CLOSED invoice
2. Modal shows: amount (defaulting to full total), source account selector
3. On confirm: invoice status → PAID, DEBIT transaction created on selected account
4. If user enters less than total: invoice still marked PAID, user adds a note explaining partial payment. No automatic carry-forward of unpaid amount.

### Module 4: Planning (Budget & Goals)

#### Budgets

Month selector at top. All active budgets for the selected month shown as progress cards.

**Budget card**: category name + icon, spent / limit, progress bar (green < 80%, yellow 80–99%, red ≥ 100%), percentage, days remaining in month.

**Creating a budget**: user picks a category and sets a limit. Toggle: "apply to this month only" or "recurring" (auto-creates for all future months until cancelled). A recurring budget generates its next instance on the first of each month.

**Budget alerts**: in-app toast when a transaction causes a budget to cross 80% or 100%. No email notifications in MVP.

**Budget vs actuals table**: shows all categories (budgeted and un-budgeted), actual spending, budget limit (if any), and variance. Useful for discovering spending in categories the user hasn't budgeted yet.

**Aggregation**: budget on a parent category sums transactions from all child subcategories.

#### Goals (Cofres)

**Goal card**: name, icon, current / target, progress bar, percentage complete, projected completion date.

**Creating a goal**: name, icon, target amount, optional deadline, optional linked account, starting current amount.

**Progress update**: user manually enters the new `currentAmount`. System records the update with a timestamp to compute average monthly contribution.

**Projections**:
- With deadline: `requiredMonthly = (target - current) / monthsRemaining`
- Without deadline: `projectedMonths = (target - current) / avgMonthlyContribution` (avg of last 3 recorded updates)

**Completion**: when `currentAmount >= targetAmount`, status → COMPLETED with a celebratory UI state. User can archive or keep visible.

### Module 5: Investments

#### Portfolio Overview

- Total invested (sum of `investedAmount` for ACTIVE investments)
- Total gross value today (sum of `currentGrossValue`)
- Total estimated IR
- Total net value
- Gross yield (%) and net yield (%)
- Breakdown by type (CDB, Tesouro, LCI/LCA, etc.)
- Upcoming maturities in the next 90 days

#### Investment Detail Card

| Displayed field | Calculation |
|---|---|
| Valor investido | `investedAmount` |
| Valor bruto atual | `currentGrossValue` (user-updated) |
| Rendimento bruto (R$) | `currentGrossValue - investedAmount` |
| Rendimento bruto (%) | `(currentGrossValue - investedAmount) / investedAmount × 10000` (basis points → %) |
| IR estimado | `grossYield × irRate / 10000` (0 if isIRExempt) |
| Valor líquido estimado | `currentGrossValue - estimatedIR` |
| Rendimento líquido (%) | derived from net value |
| Tempo | `daysSinceStart` / `daysToMaturity` |
| Taxa | formatted from `rateType` + `rateValue` |
| Liquidez | badge from `liquidityType` |

**Adding an investment**: all fields above + optional "Registrar débito na conta" checkbox.

**Updating current value**: user taps "Atualizar Valor" and enters new gross value. A value update history is kept for auditing.

**Redeeming**: user enters redemption date and actual net amount received. Status → REDEEMED. Optional "Registrar crédito na conta" checkbox creates a CREDIT transaction on a destination account.

### Module 6: Subscriptions

#### Subscription List

Active, paused, and cancelled subscriptions. Toggle active-only / all.

Each card: service name, category icon, current amount per cycle, billing cycle, next charge date (with urgency indicator), payment method, monthly equivalent cost.

#### Cost Summary

- Total monthly cost (all active, normalized to monthly equivalent)
- Total annual cost
- Biggest subscription
- Cost by category (chart)

#### Renewal Calendar

Timeline of the next 30 days with subscriptions plotted on their `nextChargeDate`. Each dot is tappable for details.

#### Price History

Accessible from each subscription's detail view. Shows a table of all price entries with `amount` and `validFrom`. Also shows the total cost paid at each price point based on how many billing cycles occurred at that price.

#### Auto-detection from Imports

After any import, the system scans all imported transactions for recurring patterns (same description + same amount, appearing at approximately monthly intervals, minimum 2 occurrences). Matches are surfaced as suggestions: "Assinatura detectada — confirmar?" User confirms or dismisses. No automatic creation.

#### Subscription Lifecycle

- **Edit**: updates current price entry if same-day, or appends new `PriceEntry` if amount changed. Always updates `nextChargeDate`, billing cycle, payment method.
- **Pause**: status → PAUSED, removed from upcoming obligations
- **Cancel**: status → CANCELLED, `cancelledAt` set. Kept in history for annual cost analysis.

## Part 4: Cross-Cutting Concerns

### Authentication

Email + password with JWT. Single user — no public registration in the UI.

- Access token: 15-minute expiry
- Refresh token: 30-day expiry, stored in `httpOnly` cookie
- All endpoints require valid access token except `POST /auth/login` and `POST /auth/register`

### In-App Notifications (MVP)

No email or push. In-app only: notification bell with unread count + toast for real-time events.

**Events**:
- Budget reaches 80% of limit (triggered on transaction save)
- Budget reaches 100% of limit (triggered on transaction save)
- Invoice due in 3 days (triggered by scheduled job — daily at 09:00)
- Subscription charge in 3 days (triggered by scheduled job — daily at 09:00)
- Investment matures in 7 days (triggered by scheduled job — daily at 09:00)

### Number and Date Formatting

- Currency: `R$ 1.234,56` (pt-BR locale)
- Dates: `dd/MM/yyyy` for display
- Backend stores all dates as `LocalDate` (no timezone — this is a personal finance app, single timezone)
- All `Instant` fields (createdAt, paidAt) stored in UTC
